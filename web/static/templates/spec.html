How the two connect

One direction only. AxioCRED's machine asks AxioIntel which places to collect, collects them on its own clock, and pushes what it found. AxioIntel never calls, schedules or reaches into AxioCRED. Both requests are signed with one shared secret, so the collector carries a single credential and no sign-in.

The leads dashboard you are using is separate from all of this. It never talks to AxioIntel.

Asking what to collect: GET /api/collector/targets

  • Auth: headers X-Axio-Timestamp (Unix seconds) and X-Axio-Signature: sha256=<hex>, the HMAC-SHA256 of "<timestamp>." + the (empty) body under AXIOINTEL_NATIVE_INGEST_SECRET. It must be within 300 s of AxioIntel's clock.
  • Answer: {generated_at, targets: [{place_id, purpose, title, last_collected_at, collect_next}]}. There is one entry per real place; purpose is the strongest any watcher claims (owned > competitor > audit). Ordered collect_next first (a paid audit waiting), then the longest-waiting.
  • Errors: 503 when not configured, 401 for a bad signature or stale timestamp.
  • Client: scripts/fetch_targets.py in Axio-Backend, copied beside collect.sh.

Sending a collection: POST /api/ingest/native

  • Signed the same way, over the exact JSON body.
  • One collection = up to 100 parts of up to 250 reviews each: {collection_id, part, parts, complete, purpose, entry, reviews, collected_seconds?}. Parts can arrive in any order; the collection finishes when all have arrived.
  • complete matters: a partial collection never has its missing reviews treated as removals. collect.sh sends --incomplete whenever the collector's own report says it did not finish (blocked, out of time, count unknown).
  • Profile: a place already watched through Apify is written into that same profile, compared only with earlier native collections. A place nobody bought gets native/<place_id>. A collection stays in the profile it started in.
  • Client: scripts/push_native.py in Axio-Backend.

Data contract

  • gmaps.Entry and gmaps.Review JSON field names are pinned by Axio-Backend's tests/test_native_contract.py. Add fields only; never rename or remove.
  • The sender forwards only its ENTRY_FIELDS (place id, cid, data id, title, category, address, counts…), so new collector fields are invisible to AxioIntel until both sides add them.
  • Reviews are deduplicated by review_id across inline, RPC and DOM passes before sending.
  • Every run writes a review_collection report per place: reported, collected, complete, stop reason (done / budget / blocked / cap / parse_error / count_unknown / error), stage, pages, blocks, identity rotations, restarts, seconds. It is kept on the VM and is what the gates below are measured from.

Promotion gates: when AxioCRED can become primary

These gates are measured, not judged by eye. All run in lab mode on the same places Apify collects, so the two can be compared place by place.

#GatePass when
G1Proxies in placeA flat-price ISP/residential pool is on the VM; a deliberately bad proxy line produces one rotation and the run still completes.
G2CoverageOver 7 nightly runs, on 90% or more of places, collected ≥ 98% of the listing's reported count, and within 2% of what Apify returned for the same place.
G3HonestyEvery place Apify had more reviews for is reported complete: false by the collector. No false "complete".
G4BlockingBlocked stops on under 5% of place-runs, and no night where every identity was refused.
G5TimeA full nightly pass of the watched places finishes inside its window, with the per-place budget under COLLECTOR_TIMEOUT_SECONDS.
G6StagingOne send-mode run against staging: collections land under the right profiles, source = native, no false removals, dashboards read them.

Cutover, once G1–G6 pass

  1. Merge Axio-CRED #7 and #8; rebuild the VM image from main.
  2. Rotate a fresh native-ingest-secret version; put only that on the VM; set COLLECTOR_MODE=send.
  3. Take #136 and #137 out of draft, rebase and re-gate, merge to staging, run the staging checks, then the prod release.
  4. Start the nightly cron. For the first two weeks, keep Apify running alongside; compare each native collection with the Apify pull of the same place.
  5. Making it primary (a later Axio-Backend change): route dashboard pulls native-first with Apify as the fallback, and scale Apify's cap down. This needs its own PR and staging run; nothing above does it.

Rollback: set COLLECTOR_MODE=lab on the VM. AxioIntel keeps Apify and simply stops receiving native pushes; the outage logic already treats a silent collector as absent.

Rules that do not move

  • Nothing here reports, flags, disputes or appeals a review to Google. A human files every submission, and nothing promises reinstatement.
  • The collector never runs in AxioIntel's axiointel Google Cloud project: it has its own provider account, its own IPs, and no link to the project Google is reviewing for Business Profile API access.
  • With proxies configured, no review request leaves the VM without one.
  • Results on the VM hold reviewers' names and words. They are kept 14 days, only until AxioIntel has them.
  • The live Apify path is never changed by collector work until the gates pass (owner's decision, 24 Sep 2026).
